# Bellum Gero World Builder - Dedicated TRE Publishing

World Builder production content is published into its own generated overlay archive:

`bg_worldbuilder.tre`

Normal Bellum Gero TRE development remains in `bg_custom1.tre`. Other developers can continue exchanging and editing `bg_custom1.tre` exactly as before.

## Ownership boundary

`bg_custom1.tre` is normal Bellum Gero custom content.

`bg_worldbuilder.tre` is generated by World Builder and must never be hand-edited. It contains only:

- affected `snapshot/<planet>.ws` files,
- project-specific `object/building/worldbuilder/...` files,
- project-specific `interiorlayout/worldbuilder/...` files,
- any future archive paths explicitly generated by World Builder.

For an affected planet, World Builder starts from the current lower-level snapshot and adds the approved World Builder nodes. This is necessary because TRE archives do not merge two copies of the same `snapshot/<planet>.ws` file.

## Load order

The intended order is:

1. `bg_worldbuilder.tre`
2. `bg_custom1.tre`
3. `default_patch.tre`
4. the normal SOE TRE stack

The dedicated archive must have higher priority than `bg_custom1.tre` so its patched snapshot is selected for planets containing World Builder content.

Load-order activation is a one-time client/server configuration step and should only be performed after validating a dedicated-TRE smoke test.

## Normal commands

The installer places a `wb` launcher in `~/.local/bin`.

Status:

```bash
wb status
```

List projects:

```bash
wb projects
```

Publish or update one project:

```bash
wb bake project_name
```

Rebuild the current approved set without changing membership:

```bash
wb bake
```

Unpublish one project without deleting its `.wbp`:

```bash
wb remove project_name
```

Deploy an add-only candidate:

```bash
wb deploy
```

For an update/removal, run the `refreshpublished` commands printed by `wb bake` while the old World Builder TRE is still active, shut Core3 down, then run:

```bash
wb deploy refreshed
```

## Candidate behavior

`wb bake` always rebuilds the complete desired World Builder overlay. It never modifies active client/server TRE files.

The candidate directory contains:

- `bg_worldbuilder.tre`
- `generated_templates.lua`
- `worldbuilder_publish.json`
- `worldbuilder_ids.json`
- `worldbuilder_oid_registry.json`

## Stable structural OIDs

Structural OIDs remain in the dedicated World Builder range:

`0x60000000-0x6FFFFFFF`

Logical project objects retain their existing OIDs across rebuilds. Removed logical keys are retained as tombstones and are never reassigned to another key.

## Dependencies on bg_custom1

A new `bg_custom1.tre` does not automatically require a World Builder rebuild.

The deployed state tracks only source records that the World Builder overlay actually depends on, including affected planet snapshots and structural source files used to generate project-specific assets.

`wb status` reports `CURRENT` when those records are unchanged even if unrelated content inside `bg_custom1.tre` has changed.

If a tracked dependency changes, `wb status` reports `STALE` and instructs you to run:

```bash
wb bake
```

`wb deploy` also rechecks those dependencies and refuses to deploy a candidate that was built against stale source records.

## Other developer workflow

No changes are required for other developers.

They continue:

1. receive the current `bg_custom1.tre`;
2. make their normal TRE edits;
3. repackage it as `bg_custom1.tre`;
4. share it through the existing Discord/Google Drive workflow.

World Builder never requires them to edit, rebuild, or understand `bg_worldbuilder.tre`.

## Source control

`worldbuilder_oid_registry.json`, `worldbuilder_publish_set.json`, and `worldbuilder_deployed_state.json` are production state and should be retained in source control.

The generated candidate directory, local config, structural reference extraction, and `.wbp` development files remain local/ignored as already configured.

## Deployment backups

`wb deploy` keeps transactional safety backups outside the Git worktree under:

`~/worldbuilder_deploy_backups/<timestamp>/`

The backup directory mirrors each original destination path so client and server
files with the same filename cannot collide. If deployment promotion fails, the
publisher continues using these backups for automatic rollback.

These backup directories are operational recovery data and are not committed to
the Bellum Gero repository.
