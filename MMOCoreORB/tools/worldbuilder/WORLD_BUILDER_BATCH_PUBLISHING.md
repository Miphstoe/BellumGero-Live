# Bellum Gero World Builder - Dedicated TRE Publishing

Travel-enabled WBP V3 projects add `worldbuilder_travel_points.lua` to every
candidate. It is generated deterministically and merges into the stock planet
travel tables. Duplicate names and World Builder destinations inside the unsafe
128m shuttle-association radius fail candidate generation.

Configure `server_travel_lua_target` beside `server_template_lua_target`.
`deploy-set` stages, verifies, backs up, promotes, and rolls back the TRE,
generated template Lua, and generated travel Lua together. Travel metadata and
hashes are recorded in the manifest/deployed state. Travel-only changes alter
the full fingerprint but not the structural fingerprint, so they do not require
`/wb refreshpublished`; old state without a structural fingerprint falls back
conservatively. A cold Core3 restart is required after travel deployment.

World Builder production content is published into its own generated overlay archive:

`bg_worldbuilder.tre`

Normal Bellum Gero TRE development remains in `bg_custom1.tre`. Other developers can continue exchanging and editing `bg_custom1.tre` exactly as before.

## Ownership boundary

`bg_custom1.tre` is normal Bellum Gero custom content.

`bg_worldbuilder.tre` is generated by World Builder and must never be hand-edited. It contains only:

- affected `snapshot/<planet>.ws` files,
- project-specific `object/building/worldbuilder/...` files,
- project-specific `interiorlayout/worldbuilder/...` files,
- any future archive paths explicitly generated by World Builder.

`bg_mtg_assets.tre` owns the MTG appearance, mesh, shader, and texture
dependencies referenced by Ship Scenery wrappers. World Builder resolves these
assets from the lower TRE stack and does not copy them into its generated
archive. Bellum Gero's one canonical
`misc/object_template_crc_string_table.iff` remains owned by `bg_custom1.tre`.

For an affected planet, World Builder starts from the current lower-level snapshot and adds the approved World Builder nodes. This is necessary because TRE archives do not merge two copies of the same `snapshot/<planet>.ws` file.

## Load order

The intended order is:

1. `bg_worldbuilder.tre`
2. `bg_custom1.tre`
3. `bg_mtg_assets.tre`
4. `default_patch.tre`
5. the normal SOE TRE stack

The dedicated archive must have higher priority than `bg_custom1.tre` so its patched snapshot is selected for planets containing World Builder content.

Load-order activation is a one-time client/server configuration step and should only be performed after validating a dedicated-TRE smoke test.

## Normal commands

The installer places a `wb` launcher in `~/.local/bin`.

Status:

```bash
wb status
```

List projects:

```bash
wb projects
```

Publish or update one project:

```bash
wb bake project_name
```

Rebuild the current approved set without changing membership:

```bash
wb bake
```

Unpublish one project without deleting its `.wbp`:

```bash
wb remove project_name
```

Deploy an add-only candidate:

```bash
wb deploy
```

For an update/removal, run the `refreshpublished` commands printed by `wb bake` while the old World Builder TRE is still active, shut Core3 down, then run:

```bash
wb deploy refreshed
```

## Candidate behavior

`wb bake` always rebuilds the complete desired World Builder overlay. It never modifies active client/server TRE files.

Every candidate also deterministically generates the built-in Ship Scenery
`object/static/worldbuilder/` client IFFs from the canonical lower-TRE
`shared_static_tie_fighter.iff`. These assets are independent of WBP membership:
an empty publish set and removal of the last project still produce a non-empty
`bg_worldbuilder.tre` containing the curated static ship wrappers. Actual JTL
ShipObjects are never included. Catalog changes require deployment of the
rebuilt TRE and a Core3 restart.

Bellum Gero keeps exactly one `misc/object_template_crc_string_table.iff`, owned
by `bg_custom1.tre`. Ship Scenery bake validation requires every generated
shared-wrapper path to be present in that lower-stack canonical table and names
any missing path and CRC. The table is never copied, generated, or packaged in
`bg_worldbuilder.tre`; add new wrapper strings through the established
`bg_custom1.tre` TRE Patcher workflow first.

The candidate directory contains:

- `bg_worldbuilder.tre`
- `generated_templates.lua`
- `worldbuilder_publish.json`
- `worldbuilder_ids.json`
- `worldbuilder_oid_registry.json`

## Stable structural OIDs

Structural OIDs remain in the dedicated World Builder range:

`0x60000000-0x6FFFFFFF`

Logical project objects retain their existing OIDs across rebuilds. Removed logical keys are retained as tombstones and are never reassigned to another key.

## Canonical lower-TRE source stack

World Builder resolves source snapshots and structural assets from the same lower-TRE priority order configured for Core3. It reads `MMOCoreORB/bin/conf/config.lua`, finds `bg_worldbuilder.tre`, skips that generated overlay, and then searches every lower-priority TRE in order.

With the normal Bellum Gero order this begins with:

1. `bg_custom1.tre`
2. `bg_mtg_assets.tre`
3. `default_patch.tre`
4. the remaining patch/data TRE stack

This means a World Builder project can be published on a planet even when `snapshot/<planet>.ws` is not present in `bg_custom1.tre`. The publisher takes the effective lower snapshot from whichever configured TRE owns it, preserves every existing node, adds all approved World Builder projects for that planet, and writes the resulting snapshot into `bg_worldbuilder.tre`.

The generated `bg_worldbuilder.tre` is never used as a bake source. Each bake starts again from the current normal lower-TRE stack and reapplies the complete approved World Builder desired state.

The actual server TRE files are authoritative for publishing. Explicit `asset_tres` are searched only after the canonical server stack, and extracted `asset_roots` such as `WorldBuilderStructureRefs` are development fallbacks searched last.

The publisher auto-detects `MMOCoreORB/bin/conf/config.lua` when the local config remains in the standard `MMOCoreORB/tools/worldbuilder` folder. The optional `server_config_lua` setting exists only for non-standard layouts. No `config-local.lua` is required for World Builder.

## Dependency freshness

A new `bg_custom1.tre` or lower stock/custom TRE does not automatically require a World Builder rebuild.

The deployed state tracks only source records that the World Builder overlay actually depends on, including affected planet snapshots and structural source files used to generate project-specific assets. Resolution uses the same canonical lower-TRE stack during both bake and freshness checks.

`wb status` reports `CURRENT` when those resolved records are unchanged even if unrelated content inside the TRE stack has changed.

If a tracked dependency changes, `wb status` reports `STALE` and instructs you to run:

```bash
wb bake
```

`wb deploy` also resolves dependencies from the current canonical lower-TRE stack and refuses to deploy a candidate that was built against stale source records.

## Other developer workflow

No changes are required for other developers.

They continue:

1. receive the current `bg_custom1.tre`;
2. make their normal TRE edits;
3. repackage it as `bg_custom1.tre`;
4. share it through the existing Discord/Google Drive workflow.

World Builder never requires them to edit, rebuild, or understand `bg_worldbuilder.tre`.

## Source control

`worldbuilder_oid_registry.json`, `worldbuilder_publish_set.json`, and `worldbuilder_deployed_state.json` are production state and should be retained in source control.

The generated candidate directory, local config, structural reference extraction, and `.wbp` development files remain local/ignored as already configured.

## Deployment backups

`wb deploy` keeps transactional safety backups outside the Git worktree under:

`~/worldbuilder_deploy_backups/<timestamp>/`

The backup directory mirrors each original destination path so client and server
files with the same filename cannot collide. If deployment promotion fails, the
publisher continues using these backups for automatic rollback.

These backup directories are operational recovery data and are not committed to
the Bellum Gero repository.
